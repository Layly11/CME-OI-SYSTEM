# CME OI SYSTEM — เว็บไซต์และระบบจัดการ license

เว็บขายและจัดการ license ของ indicator "CME OI SYSTEM" บน MetaTrader 5
สร้างด้วย Next.js 16 (App Router, TypeScript, Tailwind v4) + PostgreSQL ผ่าน Drizzle ORM

เอกสาร requirement ฉบับเต็ม: https://claude.ai/artifact/CB4Pn6SPBkkGjMMVYBVvkT

## สถานะ (16 พ.ย. 2569)

ทำแล้ว

- หน้าบ้านครบ: หน้าแรก, แพ็กเกจ, วิธีติดตั้ง, เกี่ยวกับ, FAQ, ข้อตกลง/ความเป็นส่วนตัว/คืนเงิน/ความเสี่ยง (ฉบับร่าง)
- โครงสร้างฐานข้อมูล (`src/db/schema.ts`) + migration `drizzle/0000`–`0004` + seed แพ็กเกจ
- โมดูลไฟล์ license (`src/lib/license-file.ts`) สร้าง/อ่าน/ตรวจ/เปรียบเทียบรายชื่อรูปแบบเดิมของลูกค้า
- service เผยแพร่รายชื่อ license + เก็บประวัติ + ย้อนกลับ (`src/lib/license-publish.ts`) เขียนได้ทั้งไฟล์ในเครื่องและ Firebase RTDB
  (`src/lib/firebase-rtdb.ts` — เทสด้วย fetch ปลอม ยังไม่ได้ลองกับ Firebase จริง)
- ระบบสมาชิก: สมัคร / ล็อกอิน / session (`src/lib/auth`)
- ขั้นตอนซื้อแบบอัตโนมัติทั้งเส้น ไม่มีขั้นแอดมินอนุมัติ:
  สั่งซื้อ → ชำระด้วยบัตร → เลือกโบรกเกอร์พาร์ตเนอร์ 1 ใน 6 → กรอกเลขบัญชี MT5 → **ระบบเปิด license เองและเผยแพร่รายชื่อทันที**
  - การชำระเงินอยู่หลัง interface `PaymentProvider` (`src/lib/payment`) — ตอนนี้มีแต่ **โหมดจำลอง** (`PAYMENT_PROVIDER=mock`
    ไม่มีการตัดเงินจริง ไม่มีช่องกรอกข้อมูลบัตร) ยังไม่ได้เลือก payment gateway; webhook ของ gateway จริงเรียก `markOrderPaid()` ตัวเดียวกัน
  - โหมดจำลองถูกกัน 3 ชั้น ไม่ใช่แค่ตอนกดชำระ: (1) ตอนชำระ — ใช้ได้เองเฉพาะ `NODE_ENV=development/test`
    ที่เหลือทุกค่าต้องมี `PAYMENT_MOCK_ALLOW_IN_PRODUCTION=true` และปฏิเสธเสมอเมื่อชี้รายชื่อ license จริง
    (2) ตอนเปิด license — คำสั่งซื้อที่ชำระด้วย mock ไม่เปิด license ถ้าค่าตั้งขณะนั้นไม่อนุญาต mock
    (3) ตอนเผยแพร่ — ปลายทางเป็นรายชื่อจริงแล้วยังมี license ที่ active จากคำสั่งซื้อ mock → ปฏิเสธทั้งรอบ
  - เปิด license เมื่อคำสั่งซื้อ "ชำระแล้ว" และ "มีบัญชี MT5" ครบทั้งคู่ ไม่ว่าอย่างไหนเกิดทีหลัง (`src/lib/license/`)
    1 คำสั่งซื้อเปิดได้ครั้งเดียว บังคับโดยฐานข้อมูล (ตาราง `license_activations`) — ต่ออายุก่อนหมดนับต่อจากวันหมดอายุเดิม
  - โอนเงิน + แนบสลิป (รอบก่อน) ยังอยู่ในโค้ด แต่ซ่อนจากลูกค้าเป็นค่าเริ่มต้น (`PAYMENT_BANK_TRANSFER_ENABLED`) และรอบนี้ไม่มีขั้นยืนยันสลิป
- endpoint สำรอง `GET /api/license-file`

ยังไม่ทำ / ข้อจำกัดที่รับทราบแล้ว

- **ยังไม่ได้ import เลขบัญชีของลูกค้าเดิมที่มีอยู่แต่ใน Firebase** — ต้องทำให้เสร็จก่อนชี้ `FIREBASE_LICENSE_PATH` ไปรายชื่อจริง:
  ระบบสร้างรายชื่อทั้งก้อนจากฐานข้อมูล ถ้าเผยแพร่ก่อน import เลขเดิมที่ไม่อยู่ในฐานข้อมูลจะหายจากรายชื่อ
  (ด่านใน `firebase-rtdb.ts` กันการลบเกิน `FIREBASE_MAX_REMOVED_ENTRIES` ต่อครั้ง — เมื่อด่านปฏิเสธ ลูกค้าใหม่จะค้างที่ "กำลังเปิดใช้งาน")
  และระบบยังกันเลขซ้ำกับลูกค้าเดิมไม่ได้
- เปลี่ยนเลขบัญชี MT5 หลังเปิด license แล้ว ยังไม่รองรับ (ติดต่อทีมงาน)
- ยังไม่มีการส่งอีเมล (ลิงก์ดาวน์โหลด, แจ้งเตือนก่อนหมดอายุ), หน้าดาวน์โหลดไฟล์ (`download_assets`) และ LINE OA
  — หน้าเว็บจึงบอกลูกค้าให้รับไฟล์ติดตั้งจากทีมงานทาง LINE (ไม่มีข้อความสัญญาเรื่องอีเมลแล้ว; เมื่อทำอีเมล/ดาวน์โหลดเสร็จให้แก้ข้อความกลับ)
  ถ้าไม่ตั้ง `NEXT_PUBLIC_LINE_URL` ตอน build ข้อความ "ติดต่อทาง LINE" ทุกจุดจะเป็นข้อความเปล่าไม่มีลิงก์ (เซิร์ฟเวอร์เตือนตอนเริ่ม)
- payment gateway จริง (Opn / 2C2P / GB Prime Pay / Stripe) + webhook
- ไม่มีอะไรตรวจ IB: ระบบบันทึกแค่โบรกเกอร์ที่ลูกค้าเลือก (`mt5_accounts.partner_broker_code`), `ib_status` เป็น `unverified` ทั้งหมด
- หน้าแอดมินยังเป็นโครง (ข้อมูลตัวอย่าง) — คำสั่งซื้อที่ชำระแล้วแต่เปิด license ไม่ได้ (license ถูกระงับ/เป็นตลอดชีพอยู่แล้ว/ชำระแบบจำลอง)
  ลูกค้าเห็น "ชำระแล้ว แต่เปิดใช้งานอัตโนมัติไม่ได้ กรุณาติดต่อทีมงาน" ทีมงานต้องดูจาก audit log `license.activate_blocked` แล้วจัดการเอง
  (ระบบตรวจบัญชีซ้ำก่อนพาไปชำระเงินแล้ว แต่ถ้าเงินเข้ามาอยู่ดี ยังไม่มีเครื่องมือคืนเงิน/ย้ายคำสั่งซื้อ)

- Google/LINE login
- ราคาแพ็กเกจจริง, ลิงก์ LINE, ชื่อบริษัท

## การเปิด license อัตโนมัติและการเผยแพร่รายชื่อ

ลำดับ: บันทึกลง PostgreSQL ให้เสร็จ (commit) ก่อน แล้วจึงสร้างรายชื่อทั้งก้อนจากฐานข้อมูลและเขียนทับปลายทางผ่าน `publishLicenseFile()`
การเผยแพร่ถูกเรียงคิวทั้งระบบด้วย advisory lock ของ PostgreSQL (`src/lib/license/publish-sync.ts`): ผู้ที่ได้ lock ทีหลังอ่านฐานข้อมูล
ใหม่กว่าเสมอ รายชื่อเก่าจึงไม่ถูกเขียนทับรายชื่อใหม่ในการทำงานปกติ ข้อยกเว้นคือ connection ที่ถือ lock ตายกลางคัน
(ฐานข้อมูล failover / pooler รีสตาร์ต) — งานที่หลุด lock อาจเขียนรายชื่อเก่าลงไปชั่วครู่ ระบบรอให้งานนั้นจบแล้วเขียนซ้ำจากฐานข้อมูล
ภายใน lock ทันที (audit `license_file.publish_lock_lost`) ถ้ารอบซ่อมนั้นทำไม่ได้จะรายงาน `publish_failed` และต้องรัน `npm run license:publish`
request ไป Firebase มีเวลาจำกัด 10 วินาทีต่อครั้ง จึงไม่ถือ lock ค้างไม่มีกำหนด
"วันนี้" ที่ใช้ตัดรายที่หมดอายุออกจากรายชื่อคือวันที่ตามเวลาไทย (ไม่ขึ้นกับ timezone ของเซิร์ฟเวอร์) เหมือนการต่ออายุและหน้าสมาชิก

ถ้าเผยแพร่ไม่สำเร็จ (ปลายทางล่ม, ด่านกันพลาดปฏิเสธ, หรือ `LICENSE_STORAGE` ตั้งผิด): license ยัง active ในฐานข้อมูล,
บันทึก audit `license_file.publish_failed`, ลูกค้าเห็นสถานะ "กำลังเปิดใช้งาน" (ไม่ใช่หน้า error) **ไม่มีงานเบื้องหลังที่ลองใหม่เอง** —
การเผยแพร่ถูกลองใหม่เมื่อมีการเปิด license ครั้งถัดไป, ลูกค้ากด "ตรวจสอบสถานะอีกครั้ง", หรือรันเอง (ทำซ้ำได้โดยไม่มีผลซ้ำ):

```bash
npm run license:publish                 # เก็บตกคำสั่งซื้อที่ยังไม่ได้เปิด license แล้วเขียนรายชื่อไปปลายทาง "เสมอ"
npm run license:publish -- --if-changed # เขียนเฉพาะเมื่อรายชื่อหรือปลายทางต่างจากครั้งล่าสุดในประวัติ (ไม่ได้ตรวจปลายทางจริง)
```

- `--if-changed` (และการเผยแพร่อัตโนมัติของเว็บ) ตัดสิน "ไม่มีอะไรเปลี่ยน" จากประวัติในฐานข้อมูล ไม่ได้อ่านปลายทาง:
  ถ้าปลายทางถูกแก้มือ/restore/ไฟล์หาย ต้องรันแบบไม่มี `--if-changed` การเปลี่ยน `LICENSE_STORAGE`/`FIREBASE_LICENSE_PATH`
  ระบบตรวจพบเองและเขียนปลายทางใหม่ในการเผยแพร่ครั้งถัดไป (เทียบกับ `storage_url` ของแถวประวัติล่าสุด)
- **ด่านกันพลาดปฏิเสธ = การเปิดใช้งานของลูกค้าใหม่ทุกคนหยุด** จนกว่าจะมีคนเข้ามาแก้ (ปุ่มลองใหม่และสคริปต์ล้มแบบเดียวกัน):
  ด่าน "บัญชีหายเกิน `FIREBASE_MAX_REMOVED_ENTRIES`" เทียบกับค่าปัจจุบันใน Firebase เสมอ จึงไม่หายเอง
  ต้องตั้งการแจ้งเตือนจาก audit `license_file.publish_failed` (หรือ log `[license] เผยแพร่รายชื่อไม่สำเร็จ`)

ปลายทางมาจาก `LICENSE_STORAGE` (`local` = ไฟล์ใน `LICENSE_LOCAL_DIR`, `firebase` = RTDB; ไม่ตั้ง `FIREBASE_LICENSE_PATH` = path ทดสอบ `Data_test`)
ค่าที่ไม่รู้จัก (`Firebase`, พิมพ์ผิด) หรือไม่ตั้งค่านอก `NODE_ENV=development/test` (production, `next start`, สคริปต์) ถือว่าผิด:
เซิร์ฟเวอร์ไม่ให้บริการ (ทุกคำขอได้ 500 พร้อมสาเหตุใน log) / สคริปต์ไม่ทำงาน — ระบบไม่ถอยไปเขียนไฟล์ในเครื่องเงียบๆ

## ก่อนเปิดระบบจริง (ชี้ `FIREBASE_LICENSE_PATH` ไป `CME_Data/Customer Data/Data`)

ทำให้ครบทุกข้อ ตามลำดับ:

1. **import รายชื่อลูกค้าเดิมจาก Firebase เข้าฐานข้อมูล** (ยังไม่มีสคริปต์) — ไม่ทำ เลขเดิมจะหายจากรายชื่อ และด่านกันพลาดจะปฏิเสธการเผยแพร่
2. **แยกข้อมูลทดสอบออกจากระบบจริง** — การชำระเงินจำลองเปิด license ให้ฟรี จึงต้องไม่มีทางไหลเข้ารายชื่อจริง:
   - ดีที่สุด: ระบบจริงใช้ **ฐานข้อมูลใหม่** และ **ห้ามใช้ `DATABASE_URL` ร่วมกับระบบที่เปิด `PAYMENT_PROVIDER=mock`** ไม่ว่ากรณีใด
   - ถ้าต้องใช้ฐานข้อมูลเดิม: `npm run license:purge-mock` (ดูว่าจะทำอะไร) แล้ว `npm run license:purge-mock -- --apply`
     — license ที่สร้างจากการชำระจำลองถูกทำให้หมดอายุ, license เดิมที่ถูกต่ออายุแบบจำลองได้วันหมดอายุเดิมคืน, คำสั่งซื้อจำลองถูกยกเลิก
   - ด่านในโค้ด (ไม่ต้องพึ่งการจำ): คำสั่งซื้อจำลองไม่เปิด license เมื่อปิด mock แล้ว และการเผยแพร่ไปรายชื่อจริงถูกปฏิเสธทั้งรอบ
     ตราบที่ยังมี license ที่ active จากคำสั่งซื้อจำลอง — ผลข้างเคียง: ลูกค้าจริงจะค้าง "กำลังเปิดใช้งาน" จนกว่าจะล้างข้อมูล
3. ตั้ง `LICENSE_STORAGE=firebase`, `FIREBASE_DATABASE_URL`, `FIREBASE_SERVICE_ACCOUNT_JSON`, เว้น `PAYMENT_PROVIDER` ว่าง
   (หรือเป็น gateway จริงเมื่อมี), ตั้ง `NEXT_PUBLIC_LINE_URL` **ก่อน build**
4. ทดสอบกับ path ทดสอบ (`Data_test`) และบอทจริงอย่างน้อย 1 บัญชีก่อน แล้วจึงเปลี่ยน path
   หลังเปลี่ยนปลายทางให้รัน `npm run license:publish` 1 ครั้งและตรวจค่าใน Firebase ด้วยตา
5. **ตั้ง cron รัน `npm run license:publish -- --if-changed` อย่างน้อยวันละครั้ง** (เช่น 00:05 เวลาไทย) — license ที่หมดอายุถูกตัดออกจากรายชื่อ
   เฉพาะตอนเผยแพร่ ถ้าไม่มี cron รายที่หมดอายุจะสะสม พอเกิน `FIREBASE_MAX_REMOVED_ENTRIES` (ค่าเริ่มต้น 10) ทุกการเผยแพร่จะถูกปฏิเสธ
   และลูกค้าใหม่ทุกคนค้างที่ "กำลังเปิดใช้งาน" (ห้ามแก้ด้วยการเพิ่มเพดานเป็นค่าประจำ — เพดานคือสิ่งที่กันรายชื่อหายทั้งก้อน)
6. ตั้งการแจ้งเตือนเมื่อมี audit `license_file.publish_failed`, `license_file.publish_lock_lost`, `license.activate_blocked`, `license.activate_failed`
7. บอกผู้ว่าจ้าง: หลังเปิดระบบ ห้ามแก้รายชื่อมือใน Firebase Console (การเผยแพร่ครั้งถัดไปจะเขียนทับ และ `--if-changed` จะไม่รู้ว่าถูกแก้)

## เริ่มพัฒนาในเครื่อง

ต้องมี Node.js 20 ขึ้นไป

```bash
npm install
cp .env.example .env.local      # แล้วเติมค่า
npm run dev                     # http://localhost:3000
npm test                        # unit test
npm run test:db                 # integration test กับ PostgreSQL จริง (ต้องตั้ง TEST_DATABASE_URL)
npm run test:e2e                # ทดสอบ flow ผ่าน HTTP กับเซิร์ฟเวอร์ที่รันอยู่ (ดูหัวไฟล์ scripts/e2e.mjs)
```

ฐานข้อมูล (ใช้ Neon หรือ Supabase ฟรี หรือ PostgreSQL ในเครื่อง)

```bash
npm run db:migrate              # สร้างตารางจาก drizzle/*.sql
npm run db:seed                 # ใส่แพ็กเกจตั้งต้น
npm run db:studio               # เปิด GUI ดูข้อมูล
```

แก้ schema แล้วให้รัน `npm run db:generate` เพื่อสร้างไฟล์ migration ใหม่ จากนั้น `npm run db:migrate`

## รูปแบบไฟล์ license (สำคัญ)

indicator ของลูกค้าอ่านไฟล์ข้อความรูปแบบ

```
id766232.2027.07.02,id97086397.2027.07.01,id26763436.2100.12.30
```

- `id` + เลขบัญชี MT5 + `.` + ปี.เดือน.วัน ที่หมดอายุ คั่นด้วยคอมมา ไม่มีช่องว่าง
- ตลอดชีพใช้ `9999.01.01` (ไฟล์เดิมมี `2099.12.29` / `2100.12.30` ด้วย ระบบอ่านได้ทุกแบบ)
- บอทจะทำงานก็ต่อเมื่อเลขบัญชีอยู่ในไฟล์และยังไม่หมดอายุ (ลูกค้ายืนยัน)

ข้อควรระวังก่อนใช้จริง

1. ยังไม่เห็นโค้ดฝั่ง indicator — ต้องเอาไฟล์ที่ระบบสร้าง (`buildLicenseFile`) ไปทดสอบกับบอทจริงอย่างน้อย 1 บัญชี
2. ถาม URL ที่ indicator อ่านอยู่ตอนนี้ และความถี่ที่อ่าน ถ้าเปลี่ยนโดเมน ลูกค้าทุกคนต้องแก้ค่า WebRequest ใน MT5
3. URL ของไฟล์นี้ต้องไม่ล่ม — production ควรวางบน object storage + CDN แยกจากเว็บ ไม่ใช่ `/api/license-file`
4. นำเข้าลูกค้าเดิมจากไฟล์ปัจจุบันก่อนสลับระบบ (`parseLicenseFile` ใช้ได้เลย)

## Deploy

แนะนำ Vercel (เว็บ) + Neon (PostgreSQL) ทั้งคู่มีแพ็กเกจฟรี

1. push โค้ดขึ้น GitHub แล้ว import โปรเจกต์ใน Vercel
2. ตั้ง environment variables ตาม `.env.example` — `LICENSE_STORAGE` ต้องตั้งเองเสมอ (ไม่ตั้ง เซิร์ฟเวอร์ production ตอบ 500 ทุกคำขอ — ดูสาเหตุใน log)
   และทำตามหัวข้อ "ก่อนเปิดระบบจริง" ก่อนชี้ไปรายชื่อ license จริง
3. รัน migration กับฐานข้อมูล production: `DATABASE_URL=... npm run db:migrate && npm run db:seed`
4. ตั้งโดเมนของลูกค้า และโดเมนแยกสำหรับไฟล์ license

ทุกบัญชี (Vercel, Neon, โดเมน, Google/Meta) ควรเปิดในชื่อของลูกค้า
